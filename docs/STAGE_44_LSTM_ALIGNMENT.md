# Stage 44 — LSTM Training Alignment

## Stage-43 standing concern

Stage-43 `dqn_training.py` used a stand-in forecast:

```python
forecast_feature = max(0.05, min(2.0, _aggregate_load(grid) / 20.0))
```

This sat in `[0.74, 1.08]` during training, while evaluation fed
the actual LSTM prediction which lands in `[0.30, 0.49]`. The two
distributions did not overlap (`docs/STAGE_43_1_LSTM_TRAINING_ALIGNMENT.md`).

## What Stage-44 changes

`backend/experiments/stage44_dqn_training.py` replaces the stand-in
with:

```python
# Build the LSTM forecaster once per run (RNG-forked).
lstm_forecaster = DemandForecaster()
# Per-step LSTM input: past observations only.
lstm_history.append((load, gen, weather_proxy))
# Repair R1: real LSTM prediction (no future data).
forecast = _lstm_predict(lstm_forecaster, list(lstm_history))
```

The LSTM is **constructed once** at the start of training (inside
`torch.random.fork_rng` so its random weights cannot perturb the
DQN's torch RNG stream) and **frozen** — no per-step retraining,
no per-episode retraining. The same frozen LSTM architecture +
weights are reused across every training episode.

## No future leakage

The LSTM history is a `collections.deque(maxlen=10)` populated
only with `(load, gen, weather)` tuples from timesteps `t <=
current_step`. There is no `t+1`, no future fault information, no
future load, no future renewable generation. This contract is
verified by:

* `test_lstm_no_future_leakage` (existing in
  `backend/tests/test_stage43_integration.py`) — verifies that the
  deque never grows beyond `maxlen=10` and that the newest element
  was appended at the current step.
* `test_training_lstm_no_future_leakage` (added in
  `backend/tests/test_stage44_alignment.py`) — verifies that
  `_lstm_predict(history)` only consumes the history deque and
  cannot reach forward.
* `test_training_lstm_is_real_lstm` (added in
  `backend/tests/test_stage44_alignment.py`) — verifies that the
  forecast feature passed to `build_extended_state` during training
  is the output of `DemandForecaster.predict(history)`, NOT
  `aggregate_load/20`.

## What is not changed

* The LSTM architecture (`models/lstm_model.LSTMForecaster`) is
  unchanged. It is the same model that evaluation uses.
* The LSTM is **never trained on evaluation data.** The LSTM
  pretraining happens inside `DemandForecaster._pretrain` using the
  synthetic dataset generated by `generate_synthetic_data(n=500)`;
  no evaluation scenario, fingerprint, or measurement is ever fed
  to it.
* The LSTM history channel layout `(load, gen, weather)` is the
  same at training and evaluation.

## Training-time vs evaluation-time forecast distribution

The Stage-44 training log (`experiments/results/stage44/training_log.json`)
records per-step `forecast_feature` values. After the first run the
distributions will be compared with the evaluation-time distribution
in `experiments/results/stage43_1/lstm_alignment.json` and the gap
documented in `docs/STAGE_44_STATE_DISTRIBUTION.md`.
