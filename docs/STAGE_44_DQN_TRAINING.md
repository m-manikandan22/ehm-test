# Stage 44 — DQN Training Design

## Source

`backend/experiments/stage44_dqn_training.py::train_stage44_dqn`.

This pipeline supersedes `backend/experiments/dqn_training.py` (the
Stage-43 pipeline) for any paper claim. It implements:

* **Repair R1** — real LSTM forecast feature during training
  (`models.lstm_model.DemandForecaster.predict(history)`).
* **Repair R2** — representative training scenarios
  (`experiments.train_scenario_generator.sample_training_scenarios`).
* **Repair R4 (audit-only)** — `use_zero_init=True` zero-mean
  final-layer initialisation. Kept **only** if the isolated
  initialization audit justifies it (see
  `docs/STAGE_44_INITIALIZATION_AUDIT.md`).

The reward is *patched* to make the supercap bonus conditional on
the action's *measured* effect — see
`docs/STAGE_44_REWARD_DESIGN.md` and the
`SUPERCAP_EFFECT_DELTA` patch in `models/rl_agent.py`.

## RNG isolation

`utils.seeds.derive_stream_seeds(master_seed)` produces three
sub-seeds — `environment`, `controller`, `training` — from a
single `master_seed`. The training loop:

1. Sets `torch.manual_seed(stream_seeds["training"])` *before*
   constructing `DQNAgent`.
2. Constructs the LSTM forecaster inside
   `torch.random.fork_rng(devices=[])` and saves/restores the numpy
   global state around the construction, so the LSTM's random
   initialisation cannot leak into the DQN RNG stream.
3. Per episode: `set_global_seed(master_seed + ep)` then
   `SmartGrid(seed=master_seed+ep, rng_seed=env_seed)` where
   `env_seed = stream_seeds["environment"] + ep * 10007`. This
   decorrelates the environment stream across episodes while
   keeping the per-episode stream deterministic.

## Frozen LSTM

The LSTM is built **once** at the start of training
(`_build_frozen_lstm`) and reused across every step of every
episode. The Stage-43 concern about silent per-step LSTM rebuilding
is therefore closed: the LSTM is constructed once per training run,
its weights depend only on the `training` stream seed, and
`torch.random.fork_rng` keeps that construction from perturbing the
DQN's torch RNG. The LSTM itself is a `DemandForecaster`, which
calls `_pretrain` (30 epochs on a 500-sample synthetic dataset) at
construction; this is fast (~2 s on CPU).

The same frozen LSTM forecaster's `predict()` is called every step
of every episode. No evaluation scenario or evaluation fingerprint
is ever fed to the LSTM's training set — the synthetic dataset is
generated by `models.lstm_model.generate_synthetic_data` and
contains no measurement from the paper experiment.

## LSTM history (no future leakage)

The training loop keeps a `collections.deque(maxlen=10)` of
`(load, gen, weather)` triples; each triple is built from the
grid's *current* aggregate load and generation
(`experiments.info_flow._aggregate_grid_load_and_gen`) and the
episode's *fixed* `weather_proxy`. The deque is appended at the
*current* step (never at `t+1` or later); the LSTM input is the
*last 10 entries* of the deque, left-padded with the first entry if
fewer than 10 are available. This is the same construction as the
evaluation harness (`experiments.info_flow._compute_lstm_forecast`).

The contract is verified by:

* `tests/test_stage43_integration.py::test_lstm_no_future_leakage` —
  the deque never grows beyond `maxlen=10`.
* `tests/test_stage44_alignment.py::test_training_lstm_no_future_leakage` —
  the prediction depends only on the deque's contents.
* `tests/test_stage44_alignment.py::test_training_lstm_is_real_lstm` —
  the training forecast feature is *not* the `aggregate_load/20`
  Stage-43 stand-in (it differs by more than `1e-3` from the
  stand-in computed on the same input).

## Per-step pipeline

For each step in each episode:

1. Apply scheduled fault(s) via `grid.inject_failure(target)`.
2. `grid.update_power_flow()` (best-effort, exceptions swallowed).
3. Tick the twin registry via
   `experiments.info_flow._tick_twin_registry(grid, registry)` —
   the same helper the evaluation harness uses.
4. Append `(load, gen, weather_proxy)` to the LSTM history deque.
5. Compute `forecast = _lstm_predict(lstm_forecaster, list(history))`
   — past observations only.
6. Read twin features (`max_risk`, `mean_risk`, `high_frac`) via
   `experiments.info_flow._twin_risk_map`.
7. Build `extended = build_extended_state(rl_state, predicted_load=…,
   battery_soc=…, supercap_soc=…, twin_max_risk=…, twin_mean_risk=…,
   twin_high_frac=…)` — positions 72–77 of the 78-dim state.
8. `decision = agent.select_action(extended, predicted_load=forecast,
   grid_state=grid_state)` — physical-validity mask + ε-greedy.
9. Dispatch the action via `experiments.runner._dispatch_action`,
   then `grid.step()`, then `grid.update_power_flow()`.
10. Re-read the post-step state and build `next_extended`.
11. Compute the reward via
    `agent._compute_reward_components(grid_state, action_name=…,
    supercap_level_pre=…, supercap_level_post=…)`. The
    pre/post supercap levels come from the grid state before/after
    the step so the conditional `+2 supercap` bonus fires only
    when the action actually discharged the supercapacitor.
12. `agent.store_experience(extended, action_id, reward,
    next_extended, done=False)` — gradient step only if
    `len(buffer) >= BATCH_SIZE`.

## Replay buffer / target network / optimiser / ε-schedule

These are **unchanged** from `models/rl_agent.py::DQNAgent`:

| Component | Setting | Source |
|-----------|---------|--------|
| Optimiser | Adam, `lr=1e-3` | `DQNAgent.LR` |
| Loss | Smooth L1 (Huber) | `DQNAgent.criterion` |
| Discount | `γ = 0.95` | `DQNAgent.GAMMA` |
| Batch size | 32 | `DQNAgent.BATCH_SIZE` |
| Replay capacity | 2000 | `ReplayBuffer` |
| Target-net sync | every 20 steps | `DQNAgent.TARGET_UPDATE` |
| Gradient clip | global norm 1.0 | `_train_step` |
| ε schedule | exp decay 1.0 → 0.05, τ=200 | `_get_epsilon` |

## Checkpointing

`agent.save_checkpoint(path, seeds=…, git_sha=…, extra=…)` writes
`policy_net`, `target_net`, `optimizer`, `steps_done`, `epsilon`,
`state_dim`, `n_actions`, the per-stream seed triple, the
`git_sha`, and an `extra` block containing the training summary
(mean reward per episode, action counts per episode, scenario
labels, scenario conditions, `use_zero_init`, final ε). The
checkpoint path defaults to
`backend/experiments/checkpoints/dqn_stage44.pt`.

`DQNAgent.load_checkpoint(path, eval_mode=True)` returns an agent
frozen for evaluation: `eval_mode()` is invoked by default so the
loaded agent cannot take gradient steps, cannot write to its replay
buffer, and uses ε=0.

## Training budget (convergence analysis)

Stage-43 used 8 × 200 = 1 600 transitions. Stage-43.1
(`docs/STAGE_43_1_TRAINING_DATA_AUDIT.md`) found that the *number*
of transitions was not the limiting factor — it was *action
diversity*. Stage-44 widens the distribution first, so the budget
is no longer the binding constraint. The default budget is
24 episodes × 80 steps = 1 920 transitions (≈ 21 % more than the
Stage-43 budget) but is *evidence-driven*:

1. The first run (`experiments/results/stage44/training_log.json`,
   `master_seed=11, episodes=4, steps=40`) was a *probe* run used
   for the initialization audit. Mean reward across the four
   episodes was −86 to −97 (no longer the −150 to −200 of the
   Stage-43 degenerate policy).
2. The convergence-analysis budget candidates are
   `Budget A = 4×40`, `Budget B = 12×80`, `Budget C = 24×80`. The
   final budget is selected by:

   * Training reward stability across the last 25 % of episodes
     (variance < 25 % of the mean).
   * Validation reward (held-out training scenarios) within ±1 σ
     of the training reward.
   * Loss stability — Huber loss does not diverge.
   * Action distribution entropy — fraction of non-dominant action
     is > 5 % per scenario block (diagnostic only).
3. The default of `--episodes 24 --steps 80` matches Budget C and
   is the budget used for the validation run.

The training log records per-episode mean reward, per-episode
action counts, per-step num_failed / num_isolated, per-step
`twin_max_risk`, per-step `forecast_feature`, per-step battery SOC,
per-step supercap SOC. The completion report cites the final
budget and its justification.

## What is NOT changed

* The 78-dim extended state vector layout (`models/rl_agent.py`).
* The action catalogue and physical-validity mask
  (`models/rl_agent.py::_valid_actions_mask`).
* The evaluation scenarios A–J
  (`experiments/scenario_matrix.py`).
* The reward components — only the conditional trigger of the
  supercap bonus is patched; the magnitudes are unchanged.
* The information-flow wiring (`experiments/info_flow.py`).
